# ADR-008 — Redaction scope: the scrubber runs over every item value

## Status

Accepted. Recorded in code as `internal/evidence/redact.go`, applied in
`internal/evidence/assemble.go` before item truncation; env-name handling
in `internal/evidence/k8s.go` (`envNames`); normative wording in
`docs/02-LLD.md` §6; proven by `redact_test.go` (class table, multiple
credentials, idempotence, clean corpus), `assemble_test.go` (every item
type, scrub-before-truncation), `adversarial_test.go` (the full matrix
through the real composition, pinned by `testdata/adversarial_bundle.json`)
and the envtest spec in `internal/controller/incident_controller_test.go`.

## Context

LLD §6 placed the credential scrubber "over LogTemplate data". Playbook
Session 3.2 requires planted credentials to be absent from the assembled
bundle bytes when they are planted in pod logs **and in object
annotations** — and annotations are only the most obvious of several
allowed channels a credential can ride in on: `kubernetes.io/change-cause`
records the full `kubectl` command line (`kubectl set env … PASSWORD=…`),
Event messages quote probe output and container last words, Prometheus
and Loki errors quote the URL they failed to reach, kubelet waiting
messages quote whatever the container printed. A scrubber scoped to one
item type would leave every other channel to chance.

The primary guarantee is and stays structural: Secrets are unreachable
because the Reader has no method to ask for one and the RBAC grants no
rule (Session 3.1, reasserted here). The scrubber is defense in depth
over telemetry the collector is *allowed* to read.

## Decision

1. **Scope: every data value of every item**, in the assembler, before
   canonical bytes exist — and before the 4 KiB item truncation, so a cut
   can never leave the visible half of a credential behind. An item with
   any replaced value is marked `redacted: true`. Keys are not scrubbed:
   they are code-owned constants or DNS-label-constrained names.
2. **Classes and markers** (`«redacted:<kind>»`), applied in this fixed
   order:

   | kind | matches |
   |---|---|
   | `pem-block` | `-----BEGIN …-----` … `-----END …-----`; a BEGIN without END redacts to the end of the value |
   | `url-credentials` | the `user:password@` authority of a URL (`://user:pass@` → `://«…»@`); the user name goes too |
   | `aws-access-key` | AWS access-key ids (`AKIA`, `ASIA`, … + 16 upper-case alphanumerics) |
   | `jwt` | three base64url segments, the first starting `eyJ` |
   | `bearer-token` | `Bearer <token>` in any case; the token must be 16+ characters and carry a digit (so "Bearer authentication" in prose is not one) |
   | `opaque-token` | a run of 40+ base64 characters mixing upper case, lower case and digits; unless the run is the whole value, at most two slashes (URL paths are not base64) |
   | `credential-assignment` | `KEY=value` where KEY ends in `password`, `passwd`, `secret`, `token`, `api_key`/`api-key`, `access_key`/`access-key`; the key survives, the value (quoted or bare) does not |

   The first five are the LLD's required classes; the last two are
   defense in depth: assignments are how change-cause annotations and
   env dumps carry secrets, and opaque runs are what AWS secret keys and
   the body lines of a PEM key delivered one log line at a time look like.
3. **Replacement is removal.** The marker carries the kind and nothing
   derived from the value — no hash, no prefix, no length. Two different
   secrets of one class scrub to the identical marker.
4. **Idempotent, deterministic, silent.** Rules run in a fixed order; no
   marker matches any rule (every value class excludes `«` and `»`), so
   `Scrub(Scrub(x)) == Scrub(x)`; the original value is never logged,
   never placed in an error, never printed by a test assertion.
5. **Environment variables: names only.** A PodStatus item lists
   `container.<name>.env` as variable names in spec order; a `valueFrom`
   entry is named by its source kind — `NAME(secretKeyRef)`,
   `(configMapKeyRef)`, `(fieldRef)`, `(resourceFieldRef)` — never by the
   referenced object or key, and is never resolved. The literal `value`
   field is never read. Containers without env get no key.

LLD §6's redaction paragraph is rewritten to this in the same commit.

## Consequences

**What this buys.** One choke point: every collector's output, present
and future, crosses the scrubber because assembly is the only way into a
bundle. Planting the required classes in every allowed channel and
asserting their absence from the complete canonical bytes is a real test,
not a per-field one.

**Known false-negative classes** (stated, not solved): provider API keys
with dashes or underscores (`sk-…`, `ghp_…`) are not a modelled class and
are only caught if they happen to sit in a `KEY=value` assignment; a
password that is a plain word; HTTP Basic credentials outside a URL; a
secret split across two log lines other than a PEM body; base64 material
shorter than 40 characters; a credential glued to word characters on both
sides (no word boundary) is caught only by the opaque rule if long enough.
Regex scrubbing is defense in depth; the structural no-Secrets boundary
is the guarantee.

**Known false-positive classes**: a `next_token=…` pagination parameter or
a `--token=` flag with a harmless value; any 40+ character mixed-case
base64 payload that is not a secret; a public certificate in PEM form. A
false positive costs a `redacted` flag and one marker, never evidence
integrity.

**Accepted trade-off.** A marker in a change-cause annotation or an Event
message slightly reduces what a reader sees; a credential in a bundle a
model reads and a human approves is not a trade at all.
