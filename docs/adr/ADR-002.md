# ADR-002 — `snapshotRef` lives in status, and spec is immutable

## Status

Accepted. Recorded in code on `RollbackSpec` and `ExecutionStatus` in
`api/v1alpha1/remediationplan_types.go`; indexed in `docs/01-HLD.md` §10.

## Context

A `RemediationPlan` is reversible because the executor captures the pre-change state of
every target before it mutates anything, and stores it as a snapshot ConfigMap
(`praxis-snap-<plan-uid8>`, `docs/02-LLD.md` §13). Something in the object has to name
that ConfigMap so the rollback controller can find it.

The original research sketch placed `snapshotRef` in `spec`, alongside the declared
rollback strategy. That is wrong for two independent reasons, and they compound.

First, **ordering**: the snapshot does not exist when the plan is created. The analyzer
writes the spec; the executor takes the snapshot much later, at the `Executing`
transition. A spec field for it would be empty for the entire life of every plan that
never executes, and would have to be filled in after the fact.

Second, **immutability**: approval in Praxis is cryptographically bound. `status.approval.boundTo`
is a hash over the evidence bundle, the canonical spec, the rendered diff and the policy
revision (`docs/02-LLD.md` §8), recomputed on the approval callback *and again immediately
before execution*. Any drift voids the approval. That mechanism is what kills the
time-of-check/time-of-use gap — a human approves a specific change, not a mutable
placeholder. It only works if the spec genuinely cannot change between approval and
execution. A spec field that the executor must write is a spec field that changes after
approval, which would either break every approval or force the hash to exclude the field,
reopening the gap it was built to close.

## Decision

**`spec` is immutable after creation**, enforced by a CEL transition rule on
`RemediationPlanSpec`:

    +kubebuilder:validation:XValidation:rule="self == oldSelf"

A change of mind means a new object, not an edit. An edited plan is by definition a
different plan, because the approval was bound to the hash of the old one.

**`snapshotRef` lives in `status.execution.snapshotRef`**, written only by the executor,
immediately before the first mutation. `spec.rollback` declares *intent* only — a
`RollbackStrategy` of `RestorePreviousSpec` or `None` — and carries no reference to
machinery that does not yet exist. This deliberately departs from the research dossier's
sketch.

The same reasoning places every other executor- and controller-authored field in status:
`blastRadius`, `policyVerdict`, `simulation`, `approval`, `execution`.

## Consequences

**What this buys.** The approval hash binding is sound: nothing a controller writes can
alter the bytes a human approved. The spec/status split lands where Kubernetes API
conventions already put it — spec is desired state authored by the client, status is
observed state authored by the controller — so `kubectl` behaviour, RBAC on the `/status`
subresource, and `observedGeneration` semantics all work as an operator expects. Restricting
status writes to the executor's service account is a straightforward RBAC statement
(`docs/02-LLD.md` §16) rather than a field-level exception.

**What this costs.** A plan cannot be corrected in place. Fixing a typo in a predicate,
widening a replica bound, or retargeting an action all require creating a replacement
object, which makes the plan list noisier and pushes superseded-plan garbage collection
onto the roadmap. Callers that would naturally `kubectl edit` get a validation error
instead — clear, but unfamiliar. The immutability rule also applies to Praxis's own
controllers, so any future feature that seems to want a mutable spec field must instead
add a status field or a new object.

**Consistency requirement.** Because the snapshot reference is status, status must be
durable enough to drive recovery: partial-apply crash recovery reads progress markers
from `status.execution` to decide which targets were snapshotted and which were applied
(`docs/02-LLD.md` §13). Status is a ledger here, not a display cache.

sufficient for reversal in the first place, since every verb's inverse is known.
