# ADR-004 — Verification predicates move toward a template library

## Status

Accepted, partially implemented. v1alpha1 ships the free-form form described below;
the template library is roadmap, not built. Recorded in code on `VerificationSpec` in
`api/v1alpha1/remediationplan_types.go`; indexed in `docs/01-HLD.md` §10.

## Context

Every Praxis plan declares, before it executes, the condition that will decide whether it
worked: a PromQL predicate plus a window it must hold for. After execution the verifier
evaluates that predicate against Prometheus over the window and, on failure at the
deadline, triggers automatic rollback (`docs/02-LLD.md` §12). This pre-declared,
falsifiable success contract is one of the five things the HLD claims are missing from
the landscape, and it is the mechanism that makes "the fix worked" a measured fact rather
than an assertion.

The predicate is proposed by the LLM. That creates an obvious hazard: a model that writes
its own exam can write an easy one. `vector(1)`, a predicate over a metric that is always
present, or a window short enough that nothing has had time to degrade would all pass
trivially while proving nothing. This is the verification analogue of the problem
[ADR-001](ADR-001.md) solves for actions — an open-ended string the model controls, sitting
on the safety path.

The structural fix is the same one: replace free-form text with selection from a closed,
human-authored set. A predicate template library would let the planner pick a template
(`error-rate-below`, `pod-restarts-stable`, `latency-p99-under`) and fill typed parameters,
so the shape of the check is authored by an engineer and only its arguments come from the
model.

That library cannot be written yet, and writing it now would be guesswork. Praxis does not
yet know which predicates the benchmark scenarios actually need. `docs/02-LLD.md` §17
defines effect-based `fixPredicate`/`harmPredicate` per scenario, and those land in Phase 5.
Designing a template vocabulary before the scenarios exist would produce the wrong
vocabulary and freeze it into the API — the mistake ADR-001 explicitly avoids by extending
the action vocabulary only on benchmark demand.

## Decision

**v1alpha1 accepts free-form PromQL** in `VerificationSpec.Predicate`, bounded structurally
(`MinLength=1`, `MaxLength=2048`) but not semantically.

The hazard is contained meanwhile by a separation of duties, not by trusting the model:

- The LLM **proposes** the predicate; the **verifier evaluates it**, against Prometheus, at
  the deadline. The model never evaluates its own predicate and never sees the result in a
  position where it could influence the outcome.
- Evaluation is strict by construction: `query_range` over the window with a 15s step, and
  the predicate **passes only if every step returns at least one sample**. Boolean PromQL
  emits series only when true, so an empty step is a failure. A predicate that returns
  nothing fails; it does not pass by default.
- Prometheus being unreachable is `Failed/VerificationUnavailable`, never assumed success.
- At L2 — the day-to-day default tier — a human sees the predicate on the approval card
  before execution, and a trivial predicate is visible on inspection.

**The roadmap replaces this with a template library** the planner selects from. That work is
scheduled alongside the Phase 5 benchmark scenarios, whose `fixPredicate`/`harmPredicate`
definitions supply the empirical basis for the template set. Moving to templates is a
breaking API change and will require a new API version or a compatible additive field
(e.g. `templateRef` + `params` accepted alongside a deprecated `predicate`).

## Consequences

**What this buys.** v1alpha1 can verify anything Prometheus can express, which is what a
pre-benchmark project needs — the template set will be derived from evidence rather than
invented. The strict evaluation rule and the proposer/evaluator split mean the free-form
window is not unguarded, and rollback-on-failure keeps the cost of a weak predicate bounded:
a plan that passes a trivial check and did not actually help is a plan whose harm is still
capped by blast-radius scoring, policy, and snapshotting.

**What this costs, stated plainly.** A model can currently author a predicate that passes
without demonstrating a fix, and at L3 (auto-execute) no human reads it first. This is the
weakest link in the v1alpha1 safety chain and the project should say so rather than imply
the verification contract is airtight today. Additionally, free-form PromQL is an
unvalidated expression handed to Prometheus: it is not a cluster-mutation path, but a
pathological query is a denial-of-service surface against the metrics backend, and
`MaxLength` is the only bound on it at present. Autonomy tiers should not advance past L2
for an action class on the strength of the current predicate mechanism alone.

**Migration.** Because the template library is a known future change, `VerificationSpec` is
kept deliberately small — predicate, window, on-failure — so the eventual `templateRef`
form can be introduced without disturbing the surrounding type.

**Related.** [ADR-001](ADR-001.md) establishes the closed-vocabulary principle this ADR
defers rather than rejects; the deferral, not the principle, is what is temporary.
