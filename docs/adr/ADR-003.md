# ADR-003 — Integer `confidencePercent`, not a float

## Status

Accepted. Recorded in code on `Hypothesis.ConfidencePercent` in
`api/v1alpha1/remediationplan_types.go`; indexed in `docs/01-HLD.md` §10.

## Context

The analyzer's hypotheses are ranked, and each carries a confidence value. The obvious
encoding is a `float64` in `[0.0, 1.0]` — it is what the model emits and what a
statistician would expect.

Kubernetes API conventions forbid floating point in API types. The reason is
serialization ambiguity, not taste: JSON numbers have no defined precision, Go, Python,
Java and JavaScript clients round differently at the edges, and round-tripping a resource
through `kubectl get -o yaml` and back can change the stored bytes. In Praxis that is not
a cosmetic problem. Plan bytes are hashed — the canonical JSON of `plan.spec` is one
segment of the approval binding hash (`docs/02-LLD.md` §8) — and a value whose
serialization is client-dependent cannot be canonicalized reliably. A float confidence
could void a valid approval, or, worse, let two textually different specs hash the same
way depending on the client that wrote them.

The same objection rules out the usual workarounds: a string-encoded decimal is
canonical but pushes parsing and validation into every consumer, and `resource.Quantity`
is canonical but is designed for magnitudes with SI suffixes and reads absurdly as a
probability.

It is also worth asking what precision is actually needed. Nothing downstream consumes
confidence as a continuous quantity. It orders hypotheses, it is displayed to a human on
an approval card, and it may eventually feed a coarse threshold. No component
distinguishes 0.734 from 0.735, and a model's self-reported confidence is not calibrated
finely enough for that distinction to carry information anyway.

## Decision

Confidence is an **integer percentage**: `ConfidencePercent int32`, bounded by schema
validation to `[0, 100]`.

    // +kubebuilder:validation:Minimum=0
    // +kubebuilder:validation:Maximum=100
    ConfidencePercent int32 `json:"confidencePercent"`

The LLM's structured-output schema requests an integer in that range directly, so
conversion happens at the model boundary rather than inside Praxis. No floating-point
type appears anywhere in `api/v1alpha1`.

## Consequences

**What this buys.** Plan bytes are canonical and hash-stable across every client, which
is a precondition for the approval binding to mean anything. The bound is enforced by the
API server, so an out-of-range confidence is rejected before the object exists rather than
clamped by Praxis code. `kubectl` output is readable — `87` rather than `0.8700000000000001`.
And the type carries an honest signal about precision: an integer percent does not invite
the reader to believe the number is calibrated to three decimal places.

**What this costs.** Sub-percent precision is unavailable, and confidences arriving from a
model as floats must be rounded at the boundary, so two hypotheses at 0.734 and 0.735 tie
at 73. Ranking must therefore not rely on confidence alone to break ties — array order in
`spec.hypothesis`/hypothesis lists is the tiebreaker, and the benchmark's top-1/top-3
matching (`docs/02-LLD.md` §17.3) is defined over position, not score. If a future
component genuinely needs finer resolution, the fix is a separate integer field at a
stated scale (e.g. basis points), not a float.

**Scope.** This decision generalises: no floating-point field enters a Praxis API type.
Risk scores are integers (`BlastRadius.Score`), and quantities use
`resource.Quantity`, which is canonical by construction.

**Related.** [ADR-002](ADR-002.md) — spec immutability and the approval hash binding are
what make byte-level canonicality load-bearing rather than merely tidy.
