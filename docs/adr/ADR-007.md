# ADR-007 — Deterministic Drain-style log templating (sorted-input Drain)

## Status

Accepted. Recorded in code as `internal/evidence/logs` (`templatize.go`,
`normalize.go`, `client.go`) and the Loki collector
`internal/evidence/logs.go`; proven by `templatize_test.go` (order
independence, exemplar rule, similarity table, width fallback) and
`logs_test.go` (scope, bounds, raw-line prohibition, determinism).

## Context

LLD §6 and FR-P3-03 require LogTemplate evidence: raw Loki lines never
enter a bundle; lines are clustered "Drain (or equivalent)" into templates
carrying template text, a count and one exemplar. Playbook Session 3.2
authorises a simpler deterministic tokenizer if Drain proves heavy and
asks for an ADR either way, with the accuracy trade-off stated.

Three constraints shaped the choice:

1. **No dependency.** `internal/evidence` is a seam package: the import
   allowlist test (`internal/agents/boundary_test.go`) forbids anything
   beyond the standard library, the typed k8s API and one
   controller-runtime path. A log-parsing library cannot appear there,
   and the same test now covers the `logs` subpackage.
2. **Determinism is normative.** §6 requires identical cluster state to
   produce identical bytes and hash. Drain as published is
   *order-dependent*: the first line to arrive founds a cluster, later
   lines join or found new ones, and the template a cluster ends with
   depends on the sequence. Loki returns streams and lines in an order the
   collector does not control. An order-dependent templater would make
   the bundle hash a function of response ordering.
3. **No clock, no randomness.** Nothing on the output path may consult
   time or random state; thresholds must be constants.

## Decision

Implement Drain itself — it is small (about 150 lines) — with two
adaptations that make the result a pure function of the multiset of lines:

1. **Canonical pre-sort.** Lines are sorted bytewise before insertion.
   The algorithm is then deterministic over a canonical sequence, so any
   ordering of the same lines yields byte-identical clusters. The founding
   line of every cluster is therefore its bytewise-smallest member.
2. **Variable pre-masking.** Before tokenizing, obviously variable values
   are replaced by the wildcard `<*>`, in this order: klog headers
   (severity letter + MMDD, `I0912`); RFC 3339 timestamps;
   clock times; bare dates; UUIDs; IPv4 addresses with optional port; hex
   runs of eight or more characters that contain a digit; standalone
   numbers with an optional decimal part and a short unit suffix (`37ms`,
   `1.5Gi`, `95%`). Digits inside identifiers (`v1`, `http2`, `x2m8q`)
   have no word boundary before them and are left to the merge step.

The algorithm, exactly:

- **Normalize** each line (`Normalize`): strip ECMA-48 control sequences
  and control characters (tab becomes a space), replace invalid UTF-8,
  trim, cut at 1 KiB on a rune boundary with the cut marked `…`. Blank
  lines contribute nothing.
- **Tokenize** the masked line on whitespace.
- **Route** through a depth-2 parse tree: token count, then the first
  token — a first token carrying a digit or a wildcard routes through the
  `<*>` branch (Drain's rule: such tokens are usually variables). At most
  100 distinct first tokens own a child under one token count; further
  unseen tokens route to `<*>`. Because insertion order is canonical,
  exactly the lexicographically first 100 own a child.
- **Match** against the leaf's clusters: similarity is the fraction of
  positions whose tokens are equal; two wildcards are equal, a template
  wildcard against a concrete token is not. Threshold **0.5**; ties go to
  the earliest cluster. A line joins the best cluster at or above the
  threshold, otherwise founds a new one.
- **Merge**: positions that differ become `<*>`; the count increments;
  the exemplar is the bytewise-smallest member (under sorted insertion,
  the founding line).
- **Output**: clusters sorted by count descending, then template, then
  exemplar. Template representation: tokens joined by single spaces,
  variables as `<*>`; consecutive wildcards are not collapsed.

The collector around it (`internal/evidence/logs.go`) is equally fixed:
one code-owned LogQL selector per scope namespace, `{namespace="<ns>"}`,
with the namespace required to be a DNS label (anything else yields an
error item and no query); the window `[collectedAt − 15m, collectedAt]`;
the newest 5000 lines (Loki's default per-query cap, so the bound is
honoured server-side too); grouping per (namespace, container label);
one LogTemplate item per (container, template) carrying `namespace`,
`container`, `pods` (sorted contributors, at most eight named),
`template`, `count`, `exemplar`; at most **16** templates per collection,
the most frequent first (ties by key). A Loki error becomes an item
carrying `logql` and `error`; an empty window contributes no items and a
note. Only clusters leave the collector — the raw lines exist inside the
`Templatize` call and nowhere else.

## Determinism properties

- The output is a pure function of the multiset of normalized lines: no
  clock, no random state, no map iteration on the output path (maps are
  used for lookup only; clusters are kept in a creation-order slice).
- Proven by permutation tests: reversed, rotated, sorted and pairwise
  swapped inputs, and reversed stream/line order at the collector seam,
  produce `reflect.DeepEqual` clusters and items.
- The exemplar rule is total (bytewise minimum), so it cannot depend on
  arrival order even in principle.

## Known accuracy trade-offs

- **Pre-masking collapses constant numbers too.** `status=200` and
  `status=500` become one `status=<*>` template even when one of them
  never varies. The count still says how often the shape occurred; the
  distinction between success and failure codes is lost at the template
  level (the exemplar keeps one concrete value).
- **Depth-2 routing splits on a variable first token.** Lines whose first
  token is a word that varies without digits (`alice logged in`,
  `bob logged in`) land in different leaves and never merge. Drain shares
  this weakness; masking mitigates it only for digit-bearing tokens.
- **Threshold 0.5 can over-merge.** Same-length lines sharing a first
  token and half their tokens merge into a wildcard-heavy template; a
  template that becomes mostly `<*>` says little more than "a line of
  this length occurred".
- **Single-token lines never merge.** A base64 blob or a bare identifier
  per line yields one cluster per distinct line (similarity between two
  different single tokens is 0). Such lines are also what the scrubber's
  opaque-token rule targets, so they arrive redacted, but they can
  crowd the 16-template cap.
- **The frequency cap drops rare templates first.** Under a flood, a rare
  but diagnostic line (`fatal error: out of memory`, count 1) may be cut
  by the cap before it reaches the assembler; ADR-006 then also ranks
  LogTemplate second-lowest for retention. Raising the signal of rare
  lines is a Phase 3.4 tuning question, not a determinism one.
- **Sorted insertion is not streaming Drain.** On the same data a
  streaming Drain may found clusters from different lines and end with
  slightly different templates; neither is more correct, but results are
  not comparable with other Drain implementations line for line.

## Why this is sufficient for v0.1

The requirement is compression without raw lines, deterministically:
hundreds of value-changing sidecar lines become one item with a count and
one exemplar (measured on the benchmark in the Session 3.2 handoff and
`docs/PROGRESS.md`), the same set of lines in any order hashes
identically, and no dependency enters the seam. The diagnostic signal the
Phase 2 answer keys demand lives in PodStatus, Event, Metric and GitCommit
items; log evidence is additive. Whether it moves diagnosis accuracy is
exactly what Session 3.4's measurement grid will show, and the algorithm
sits behind `logs.Templatize` so a better one can replace it without
touching the bundle contract — at the cost of the LogTemplate bytes of a
given collection changing, which the golden tests make visible.
