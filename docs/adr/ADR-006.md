# ADR-006 — Complete evidence retention order under bundle caps

## Status

Accepted. Recorded in code as `retentionRank` in
`internal/evidence/assemble.go`; normative wording in `docs/02-LLD.md` §6;
proven exactly by the truncation-ladder cases in
`internal/evidence/assemble_test.go`.

## Context

LLD §6 caps every bundle (≤64 items, ≤4 KiB/item, ≤128 KiB total) and
prescribed a truncation priority — but only over five of the seven types
in the evidence vocabulary: `Metric > PodStatus > Event > LogTemplate >
OwnerChain`, leaving `GitCommit` and `SyncState` unplaced. Session 3.1's
assembler had to put them somewhere, and where they sit is not an
implementation detail: the retention order decides which items survive an
over-cap collection, which changes the bundle's canonical bytes, which
changes `sha256(canonicalJSON(bundle))` — the hash every RemediationPlan
cites (`spec.evidenceBundleHash`) and every approval binds to (LLD §8).
A survival policy that lives only in code is a normative contract by
accident, invisible to scenario authors and future sessions.

The `>` notation itself had a second defect: nothing said which side of
the comparison gets truncated. A reader could defensibly parse
"Metric > …" as "Metric is dropped first" or "Metric outranks the rest".

## Decision

1. The retention order covers all seven types. From **truncated first**
   (lowest retention) to **retained longest** (highest retention):

   `OwnerChain → LogTemplate → Event → PodStatus → Metric → SyncState → GitCommit`

   The five types the LLD already ordered keep exactly their relative
   positions; `SyncState` and `GitCommit` sit above them all.

2. Truncation removes one item per step: an item of the lowest-ranked
   type present, and within that type the last item in canonical
   (type, source, natural key) order — so the survivors of any cap are
   always a sorted prefix per type. Ids are reassigned after every drop;
   the final document never shows a gap.

3. Why `GitCommit` survives longest: recent-change context is the
   strongest diagnostic prior the bundle carries — "what changed just
   before this broke" — and several benchmark answer keys demand an
   `ev/gitcommit-*` citation outright. The items are also the smallest
   and scarcest in the bundle (at most one per annotated workload), so
   retaining them costs almost nothing while dropping them would
   systematically blind analysis to change-caused incidents, the most
   common real-world class.

4. Why `SyncState` sits second: it is the same "what changed" class of
   evidence — desired-state divergence reported by Argo CD/Flux — small
   and bounded (one per application). It ranks below `GitCommit` because
   a commit identity is the more specific prior: sync state says the
   cluster diverged, the commit says what arrived.

5. The order is deterministic by construction: rank is a total, pure
   function of the closed type enum (ADR-005 fixed that vocabulary), the
   within-type victim is fixed by the canonical sort, and no clock,
   randomness or map-iteration order participates. Identical inputs
   truncate identically, byte for byte.

## Consequences

**What this buys.** The survival policy is normative, reviewable and
mechanically proven: a table-driven ladder test drives all seven types
through cap pressure and asserts exactly who survives. Scenario authors
can reason about which evidence a saturated bundle will still hold.

**What this binds.** Changing any rank — including inserting a future
eighth type anywhere but the top — changes the canonical bytes and hash
of every over-cap bundle for identical cluster state. That silently
breaks golden tests, benchmark answer keys, and the evidence-hash
binding plans and approvals rely on. Any future reordering is therefore
a deliberate, versioned contract change: bump the bundle schema
`version` field (or record an equally explicit migration) in an ADR that
supersedes this one — never a quiet edit.

**Accepted trade-off.** Under extreme pressure a bundle keeps tiny
change-context items while shedding bulky telemetry; a pathological
flood of `SyncState` items could in principle evict every `Metric`. That
is bounded in practice (sync state is per-application, not per-pod) and
preferred on principle: when the bundle must forget something, it
forgets volume before it forgets causes.
